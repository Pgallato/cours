## Le protocole ICMP appliqué à IPv4 (ICMPv4)

<Definition titre="Internet Control Message Protocol (ICMP)">
    Protocole technique de la famille IP qui sert à échanger des messages de diagnostic et à signaler certaines erreurs.
</Definition>

Les messages les plus utilisés sont Echo Request, Echo Reply, Destination Unreachable (seulement certaines de ses « variantes ») et Time Exceeded.

### Messages ICMPv4

ICMP utilise des **types** de messages (8 bits), eux-mêmes répartis dans des **codes** (8 bits).

<Remark titre="Obsolescence">
    De nombreux codes ont été créés sans jamais être utilisés, et d'autres ont été abandonnés. C'est pourquoi bloquer ICMPv4 a finalement peu de conséquences.
</Remark>

{/* CORRIGÉ (reseaux.pdf p. 217 : la diapositive écrivait « Time To Leave » et décrivait le type 3 code 3 comme « protocole inatteignable »). */}

| Type | Code | Description |
| --- | --- | --- |
| 8 | 0 | Echo Request : demande d'écho |
| 0 | 0 | Echo Reply : réponse à écho |
| 11 | 0 | Time To Live Exceeded : trop de routeurs franchis |
| 11 | 1 | Fragment Reassembly Time Exceeded : expiration d'un fragment |
| 3 | 0 | Destination Network Unreachable : réseau inatteignable |
| 3 | 1 | Destination Host Unreachable : hôte introuvable |
| 3 | 3 | Destination Port Unreachable : port inatteignable |
| 3 | 4 | Fragmentation Required and DF Set : fragmentation impossible |
| 5 | 0 | Redirect Datagram to the Host : « routeur pas concerné » |

### Utilitaire ping

<Theorem type="Principe">
    `ping` émet des messages ICMP `Echo Request` et écoute les messages ICMP `Echo Reply`.
</Theorem>

On peut notamment lui préciser l'adresse de destination, l'interface de sortie, l'adresse source, ainsi que le délai et l'intervalle entre les envois.

<Animation type="echange-sequence" titre="Utilitaire ping (reseaux.pdf p. 218)" params={{scenario: 'ping'}}>
    Source → Destination : echo-request ; Destination → Source : echo-reply.
</Animation>

<Warning>
    Beaucoup de pare-feu bloquent tout ou partie d'ICMP, notamment les messages d'écho.
</Warning>

### Utilitaire traceroute

<Theorem type="Principe">
    `traceroute` exploite les messages ICMP en augmentant progressivement le « temps à vivre sur le réseau » (TTL) des paquets envoyés.
</Theorem>

Chaque routeur décrémente le champ TTL de 1. Lorsqu'il atteint zéro, le routeur émet un message ICMP « Time Exceeded », que `traceroute` interprète.

    Echo Request TTL=1 → R1 répond Time Exceeded (TTL=64) ; Echo Request TTL=2 → R1 transmet (TTL=1) → R2 répond Time Exceeded (TTL=64), relayé par R1 (TTL=63).
</Animation>

## Le protocole IGMP

<Definition titre="Internet Group Management Protocol (IGMP)">
    IGMP sert à l'établissement de flux multicast sur un réseau local.
</Definition>

Il sert à s'abonner à des flux multicast et à s'en désabonner. On l'utilise pour le multicast de flux multimédias, notamment l'IPTV, et pour le multicast technique, dont celui des protocoles de routage dynamique.

### IGMP Snooping

<Definition titre="Snooping">
    Le snooping (ici appliqué à IGMP) permet à un switch administrable de relayer certains trafics en interprétant certains protocoles.
</Definition>

Dans le cas d'un flux multicast, c'est le switch qui duplique le trafic, s'il en est capable, et uniquement vers les ports qui se sont abonnés. Il peut aussi filtrer les requêtes abusives.

## Le protocole DHCP appliqué à IPv4 (DHCPv4)

<Definition titre="Dynamic Host Configuration Protocol (DHCP)">
    DHCP alloue dynamiquement des adresses IP et fournit à un hôte, qui ne connaît encore rien du réseau, les informations de configuration souhaitées.

    DHCP a été conçu dès l'origine pour être étendu : chaque information est contenue dans un champ dit « d'extension ».
</Definition>

### Acquisition d'une adresse via DHCP

Client → serveur : **DHCPDISCOVER** ; serveur → client : **DHCPOFFER** ; client → serveur : **DHCPREQUEST** ; serveur → client : **DHCPACK**.

<Animation type="echange-sequence" titre="Acquisition d'une adresse via DHCP (reseaux.pdf p. 225)" params={{scenario: 'dhcp'}}>
    DHCPDISCOVER, DHCPOFFER, DHCPREQUEST, DHCPACK.
</Animation>

### Les principaux messages DHCP

{/* CORRIGÉ (reseaux.pdf p. 226 : la diapositive nommait le message 4 « DHCPNAK »). */}

| Code | Message | Description |
| --- | --- | --- |
| 1 | DHCPDISCOVER | Recherche d'un serveur par un client |
| 2 | DHCPOFFER | Réponse d'un serveur à une requête initiale |
| 3 | DHCPREQUEST | Réservation d'une adresse |
| 4 | DHCPDECLINE | Refus de l'adresse par le client (ex. : IP déjà utilisée) |
| 5 | DHCPACK | Confirmation de la réservation et informations supplémentaires |
| 6 | DHCPNAK | Rejet de la demande de réservation |
| 7 | DHCPRELEASE | Restitution de la réservation |
| 8 | DHCPINFORM | Demande d'informations supplémentaires |

D'autres messages ont été ajoutés par la suite.

### Les extensions courantes de DHCP

DHCP peut diffuser diverses informations de configuration, par exemple :

{/* CORRIGÉ (reseaux.pdf p. 227 : la diapositive donnait le code 5 (Name server) pour les serveurs DNS). */}

| Code | Extension | Description |
| --- | --- | --- |
| 0 | Pad | Bourrage pour alignement |
| 1 | Subnet mask | Masque de sous-réseau |
| 3 | Router | Routeur (par défaut) |
| 6 | Domain name server | Serveur(s) DNS |
| 42 | Time server | Serveur(s) NTP |
| 66 | TFTP server name | Serveur TFTP (« next server ») |
| 67 | Boot filename | Fichier de démarrage |
| 252 | Auto proxy config | WPAD (non officiel) |

### IP Address Management (IPAM)

<Definition titre="IPAM">
    Dans certaines grandes entreprises, une gestion centralisée des adresses IP est nécessaire, notamment avec IPv6.

    L'IPAM aide à planifier l'allocation des adresses, et donc une partie des informations utilisées par le DNS et le DHCP.
</Definition>

### DHCP snooping

Le principe est le même que pour l'IGMP snooping : sur les switches administrables, un « agent » DHCP est parfois lancé pour filtrer le protocole, afin d'éviter les utilisations abusives ou la pollution inutile du réseau.

### Relais DHCP

<Definition titre="Relais DHCP">
    Le relais capte les flux DHCP d'un segment (broadcast ou multicast) et les transmet à un serveur distant.
</Definition>

Les échanges entre le relais et le serveur se font en unicast ; c'est le relais qui reconstruit les multicasts et broadcasts nécessaires sur le segment.

## Le protocole ICMP appliqué à IPv6 (ICMPv6)

<Definition titre="ICMPv6">
    ICMPv6 est semblable à ICMPv4, mais ses messages ont été remaniés pour le rendre plus pertinent.
</Definition>

Cette refonte a notamment supprimé le protocole ARP et IGMP, et ajouté des mécanismes de configuration automatique.

### Neighbor Discovery Protocol (NDP)

<Definition titre="NDP">
    NDP remplace ARP par un protocole multicast qui passe par ICMP sur IPv6 : un protocole dédié n'est plus nécessaire, un message ICMP suffit.
</Definition>

De nouveaux messages apparaissent ; ils sont aussi utilisés par SLAAC (voir plus loin).

| Code | Message | Description |
| --- | --- | --- |
| 133 | Router Solicitation (RS) | Découverte de routeurs |
| 134 | Router Advertisement (RA) | Annonce de routeur |
| 135 | Neighbor Solicitation (NS) | Découverte de voisin |
| 136 | Neighbor Advertisement (NA) | Annonce de voisin |
| 137 | Redirect | Redirection de trafic émise par un routeur |

### Duplicate Address Detection (DAD)

<Definition titre="DAD">
    DAD détecte la présence d'une adresse IP en double sur le réseau.
</Definition>

Son fonctionnement est le suivant :

1. un hôte qui démarre envoie un NS ;
2. si un NA revient, l'adresse est déjà prise : une erreur est signalée et l'hôte renonce à cette adresse ;
3. si aucun NA ne revient avant la fin d'un délai (2 secondes, avec un nouvel envoi de NS au bout d'1 seconde), l'adresse est considérée comme libre et elle est affectée.

Il en existe aussi une version sécurisée, *Secure Neighbor Discovery* (SEND), récente et pas encore prise en charge par tous les systèmes.

### Path MTU Discovery (PMTUD)

<Remark titre="Rappel">
    En IPv6, les routeurs ne fragmentent plus les paquets, et la MTU minimale est de 1280 octets.
</Remark>

<Definition titre="PMTUD">
    PMTUD détecte la MTU minimale d'un chemin donné, et confie la fragmentation aux extrémités (les hôtes) pour soulager les routeurs.
</Definition>

La MTU peut varier d'une connexion à l'autre, en plus d'être limitée globalement si besoin. Elle est abaissée à chaque réception d'un message ICMPv6 de type 2, « Packet too big ».

### Multicast Listener Discovery (MLD)

<Definition titre="MLD">
    MLD remplace IGMP par des messages ICMP dédiés.
</Definition>

| Code | Message | Description |
| --- | --- | --- |
| 130 | Query | Vérification présence d'au moins un abonné |
| 131 | MLDv1 Report | Annonce présence d'un abonné |
| 143 | MLDv2 Report | Annonce présence d'un abonné |
| 132 | MLD Done | Retrait d'un abonné |

## Le protocole SLAAC pour IPv6

<Definition titre="State-Less Address Auto-Configuration (SLAAC)">
    SLAAC permet à un hôte de choisir automatiquement son numéro d'hôte au démarrage, en récupérant les informations du réseau auprès d'un routeur.
</Definition>

Au démarrage d'un hôte IPv6 :

1. l'hôte prend une adresse IPv6 Link-Local et lance DAD sur cette adresse ;
2. il émet un RS ;
3. si un routeur est présent, celui-ci répond par un RA ;
4. grâce au RA, l'hôte connaît le ou les préfixes du réseau et peut choisir un numéro d'hôte ;
5. il ajoute les éventuelles routes indiquées dans le RA.

### Techniques d'affectation d'adresses IPv6

<Definition titre="Affectation statique">
    Les adresses sont affectées à la main. C'est utile pour les serveurs, dont on doit connaître l'adresse.
</Definition>

<Definition titre="EUI-64">
    L'adresse MAC sert de clé unique pour construire le numéro d'hôte.
</Definition>

Une adresse EUI-64 se construit ainsi :

{/* CORRIGÉ (reseaux.pdf p. 241 : la diapositive disait « forcer à 1 le 2e bit du premier octet de poids fort »). */}

1. on récupère l'adresse MAC (48 bits) et on la sépare en deux moitiés ;
2. on place l'identifiant du fabricant (*MAC vendor ID*) du côté des poids forts ;
3. on insère FF:FE au milieu ;
4. on place le numéro de série (*MAC serial ID*) du côté des poids faibles ;
5. on inverse le bit U/L (7e bit du premier octet, valeur 0x02), qui passe à 1 pour une adresse MAC universelle.

<Definition titre="Temporary addresses">
    L'adresse est générée aléatoirement, par exemple à partir de l'heure. Le résultat dépend de l'implémentation.
</Definition>

<Definition titre="Cryptographically Generated Addresses (CGA)">
    Certaines données passent par une fonction de hachage pour produire une adresse stable, mais différente de l'EUI-64.
</Definition>

Le principe est le suivant :

1. on hache une clé publique avec un aléa et un compteur de tours, ce qui donne une valeur intermédiaire ;
2. on hache ensuite ensemble les 64 bits du préfixe et cette valeur intermédiaire ;
3. les 64 bits de poids faible du résultat forment l'adresse d'hôte.

<Definition titre="Stable Privacy Addresses">
    Des paramètres fixes servent à construire une adresse stable, sur un principe inspiré de CGA.
</Definition>

Ces paramètres sont le préfixe de réseau, le nom de l'interface réseau, un secret et un compteur d'adresses en double, incrémenté en cas de conflit.

## Le protocole DHCP appliqué à IPv6 (DHCPv6)

En théorie, DHCPv6 fonctionne comme DHCPv4 : le principe est le même, mais les options ont été remaniées.

### Modes d'attribution d'adresse automatique

- **SLAAC** : l'hôte s'attribue lui-même son adresse avec SLAAC et NDP, et découvre la passerelle grâce aux messages RS et RA.
- **DHCP sans état** : l'adresse est attribuée par SLAAC, et les informations complémentaires sont demandées par DHCP.
- **DHCP avec état** : DHCPv6 remplace complètement SLAAC et NDP.

### Acquisition via DHCPv6 avec état

Client → serveur : **SOLICIT** ; serveur → client : **ADVERTISE** ; client → serveur : **REQUEST** ; serveur → client : **REPLY**.

<Animation type="echange-sequence" titre="Acquisition via DHCPv6 avec état (reseaux.pdf p. 248)" params={{scenario: 'dhcpv6'}}>
    SOLICIT, ADVERTISE, REQUEST, REPLY.
</Animation>

### Particularités de DHCPv6

- Les messages DHCPv6 utilisent les adresses Link-Local et l'adresse de multicast `ff02::1:2`.
- Pour identifier les hôtes, DHCPv4 utilisait historiquement les adresses MAC ; DHCPv6 utilise les *DHCP Unique IDentifiers* (DUID).
