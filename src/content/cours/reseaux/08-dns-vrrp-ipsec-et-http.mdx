## Le protocole DNS

### À l'époque d'ARPANET : les fichiers hosts

<Remark titre="Point historique">
    Avant le DNS, pour connaître les noms associés aux adresses, on s'échangeait des fichiers.
</Remark>

<Example titre="Exemple de fichier /etc/hosts">
    ```
    127.0.0.1 localhost
    127.0.1.1 segonzac.intranet.example.net segonzac
    ::1 localhost ip6-localhost ip6-loopback
    ```
</Example>

Chaque ligne du fichier `/etc/hosts` contient une adresse IP, un nom d'hôte principal, puis un ou plusieurs alias, par exemple `127.0.1.1 host.localdomain host`.

### L'invention du DNS dans les universités américaines

Il fallait distribuer ce fichier à toutes les machines, dans toutes les universités, ce qui devenait vite pénible. Stanford a alors inventé le **Domain Name System**, et Berkeley son implémentation, **Berkeley Internet Name Domain** (BIND).

### Normalisation du DNS

Le DNS est défini par un ensemble de RFC, dont voici les principales :

| RFC | Objet |
| --- | --- |
| RFC 608 | fichier hosts |
| RFC 1034 | protocole DNS (principes) |
| RFC 1035 | protocole DNS (spécifications techniques) |
| RFC 1591 | racine et TLD historiques |
| RFC 6895 | recommandations de l'IANA |
| RFC 8484 | DNS over HTTPS |
| RFC 8499 | terminologie du DNS |
| RFC xxxx | (liste à compléter par dizaines !) |

### La structure du Domain Name System

Le DNS est une arborescence qui part d'une racine, notée « . ». Les domaines de premier niveau (TLD) forment le premier niveau de la hiérarchie, et les autres domaines les niveaux suivants.

### Les Top Level Domains

On distingue plusieurs catégories de TLD :

- les domaines historiques (`.net`, `.org`, `.com`…) ;
- les domaines ouverts (`.info`, `.ovh`, `.clothing`…) ;
- les domaines parrainés (`.edu`, `.gov`, `.gouv.fr`, `.travel`…) ;
- les domaines restreints (`.biz`, `.pro`, `.name`…) ;
- les domaines privés (`.leclerc`, `.sncf`, `.axa`…) ;
- les domaines nationaux (`.fr`, `.re`, `.us`, `.de`…).

### Les domaines de premier niveau spéciaux

Certains domaines de premier niveau sont réservés à des usages particuliers :

| TLD | Usage |
| --- | --- |
| `.invalid` | pour marquer explicitement comme invalide (RFC 6761) |
| `.arpa` | utilisé pour les zones inverses |
| `.example` | pour la documentation (RFC 6761) (parfois bloqué !) |
| `.localhost` | pour les adresses de loopback (RFC 6761) |
| `.local` | au profit du protocole Zeroconf (RFC 6762) (pas touche !) |
| `.lan` | réseau local MAIS n'est pas officiel ! |
| `.onion` | sites du réseau Tor (RFC 7686) (hors DNS classique) |
| `.test` | pour les laboratoires (RFC 6761) |

### Les Second Level Domains

Les domaines de second niveau sont rattachés à un domaine de premier niveau ; ils marquent la frontière du domaine privé. Chacun peut contenir autant de sous-domaines que nécessaire, qui peuvent eux-mêmes contenir des sous-domaines, et ainsi de suite.

### Les racines alternatives

<Definition titre="Racines du DNS">
    Lorsqu'on parle du *Domain Name System*, on fait implicitement référence à l'ICANN et aux 13 serveurs racine couramment utilisés.
</Definition>

Il existe pourtant d'autres racines :

- **AlterNIC** était le concurrent d'InterNIC avant la création de l'ICANN ; il a disparu.
- **Handshake** est un système décentralisé fondé sur une blockchain ; il vise la résilience et complète le DNS classique.
- **Namecoin** est un système décentralisé fondé sur une blockchain, propre au TLD `.bit`.
- **OpenNIC** est une racine DNS alternative qui reprend le mécanisme classique du DNS, mais sans lien avec les racines de l'ICANN et de l'IANA.
- Il existe enfin des racines **souveraines** : le Yeti DNS Project, `.chn` ou le Russian National Domain Name System.

### Types d'enregistrements

<Definition titre="Resource Records">
    Le DNS utilise des *Resource Records* pour catégoriser l'information et la distribuer.
</Definition>

Un enregistrement associe un nom à différentes données, par exemple des adresses IPv4 ou IPv6, des clés SSH ou du texte libre.

Voici les enregistrements les plus courants :

| Type | Contenu |
| --- | --- |
| A | adresse IPv4 |
| AAAA | adresse IPv6 |
| PTR | nom réel (à partir d'une adresse) |
| SOA | racine d'une zone autoritaire |
| CNAME | alias |
| NS | serveurs de noms autoritaires |
| MX | relais de courrier |
| TXT | texte libre |
| DS | signature de zone (DNSSEC) |

### Start Of Authority (SOA)

<Definition titre="SOA">
    L'enregistrement SOA indique qu'un serveur fait autorité pour un sous-domaine donné.
</Definition>

| Champ | Signification |
| --- | --- |
| Master NS | serveur maître de zone |
| Contact | adresse de courriel du gestionnaire du serveur maître |
| Serial | numéro de version pour la zone |
| Refresh | écart en secondes pour les mises à jour (secondaires, esclaves) |
| Retry | délai en secondes entre deux requêtes si la première a échoué |
| Expire | délai en secondes pour déclarer la zone invalide si le primaire est injoignable |
| Min. TTL | durée de vie en secondes d'une réponse dans le cache |
| Neg. TTL | durée de vie en secondes des demandes d'enregistrements inexistants |

### Circulation de la requête

1. Le client cherche l'adresse de `www.free.fr` : il envoie sa requête à son serveur DNS de rattachement, le résolveur.
2. Le résolveur ne connaît ni ce nom ni ce TLD : il interroge un serveur racine.
3. Le serveur racine le renvoie vers un serveur qui fait autorité pour .FR.
4. Le résolveur repose sa question pour le domaine de second niveau.
5. Le serveur .FR lui indique une nouvelle autorité, celle de Free.
6. Le résolveur interroge alors les serveurs DNS de Free, qu'il connaît désormais.
7. Il obtient enfin la réponse définitive,
8. qu'il renvoie au client.

### Client DNS sous Windows

<Definition titre="Client DNS">
    Il centralise les requêtes DNS pour offrir un cache, et parfois un peu « d'intelligence ».
</Definition>

Sous Windows, c'est un service appelé « Client DNS » qui joue ce rôle. Sans lui, les résolutions fonctionnent moins bien, voire pas du tout selon les versions. On peut le piloter avec des CmdLets PowerShell.

### Client DNS historique sous Linux

Sous Linux, les fichiers historiques de résolution de noms, dont le fameux `/etc/hosts`, sont exploités à travers le « *Name Service Switch* » (NSSwitch).

Le client historique se résume essentiellement à NSSwitch, qui choisit entre les fichiers (`hosts`, `resolv.conf`) et le DNS, entre autres sources. On peut lui ajouter un cache : NSCD, le *Name Service Caching Daemon*.

### Client DNS de systemd : systemd-resolved

systemd-resolved a pour objectif d'éliminer certains mécanismes obsolètes ou qui ne sont plus activement maintenus. En pratique :

- il agrège différentes sources de noms ;
- il émule un résolveur local ;
- il fait du cache et de la vérification de signatures ;
- il remplace `/etc/resolv.conf` par un lien symbolique.

<Example titre="Exemple de configuration simple et largement utilisée">
    ```ini
    [Resolve]
    DNS=192.168.1.254
    Cache=yes
    DNSStubListener=yes
    ReadEtcHosts=yes
    ```
</Example>

## Pour aller plus loin : le protocole VRRP

<Definition titre="Virtual Router Redundancy Protocol (VRRP)">
    VRRP affecte une adresse IP « flottante » à plusieurs routeurs ou services, afin d'avoir un équipement « actif » et un ou plusieurs équipements « de secours ».
</Definition>

Son fonctionnement est le suivant :

- les systèmes se mettent d'accord sur la possession d'un jeton, qui autorise à utiliser l'adresse IP ;
- les participants s'annoncent sur une adresse de multicast ;
- ils s'attribuent une adresse MAC virtuelle ;
- en cas de bascule, des paquets ARP gratuits permettent au nouvel actif de reprendre le contrôle de l'adresse IP virtuelle.

## Pour aller plus loin : le protocole IPSec

<Definition titre="Internet Protocol Security (IPSec)">
    IPSec signe ou chiffre les paquets IP.
</Definition>

Un « contexte de sécurité » (ou association de sécurité) définit le chiffrement du flux pour un ou plusieurs sous-réseaux IP, avec une clé donnée.

La négociation des clés est généralement assurée par *Internet Key Exchange* (IKE). Selon les implémentations, l'authentification peut passer par *Extensible Authentication Protocol* (EAP) et ses modules.

## HTTP, un protocole à tout faire ?

<Definition titre="HyperText Transfer Protocol (HTTP)">
    À l'origine, HTTP sert simplement à transporter sur le Web des données de différents formats.

    Aujourd'hui, il transporte des pages Web et leur contenu, voire bien plus.
</Definition>

### Fonctionnement

<Example titre="Requête HTTP simple">
    ```http
    GET / HTTP/1.1
    Host: www.perdu.com
    ```
</Example>

Les principaux verbes (ou méthodes) sont `GET`, `POST`, `HEAD`, `PUT`, `DELETE` et `CONNECT`.

HTTP est un protocole **sans état**, comme UDP. Cependant, les en-têtes, notamment les cookies, permettent de construire un mode connecté et de suivre une « session » du point de vue de l'application Web, à la manière de TCP.

### Utilisation

HTTP est si répandu qu'il a été adapté à de nouveaux usages :

- **WebDAV** pour les transferts de fichiers dans les deux sens (dont CalDAV et CardDAV) ;
- les **WebServices** pour les échanges entre machines (REST, SOAP…) ;
- les **WebSockets** pour les flux full-duplex entre clients et serveur (dont le streaming) ;
- **WebRTC** pour les flux multimédias pair à pair entre navigateurs (dont RTP) ;
- **DNS over HTTP (DoH)** pour contourner la censure DNS.

Il est donc devenu difficile à filtrer.

### Dérive potentielle

<Remark titre="Idée de réflexion">
    À force de tout faire passer par HTTP, on oublie les couches inférieures et les protocoles existants, et on réinvente la roue, parfois en mieux, parfois en moins bien.
</Remark>

<Theorem type="Conseil">
    Avant de concevoir une solution, regardez l'existant : il y a sûrement déjà un outil ou un protocole qui fait ce dont vous avez besoin, moyennant une adaptation mineure.
</Theorem>
