## Principes élémentaires communs à TCP et UDP

### Le port

<Definition titre="Port">
    Le port sert à multiplexer et démultiplexer des communications sur un même hôte.
</Definition>

- S'encode sur 16 bits, donc de 0 à 65535.
- Des numéros sont réservés et enregistrés à l'IANA.
- Un port donné côté serveur est souvent un indicateur fiable du service qui l'utilise.
- Parfois port source et port destination peuvent être identiques.

Exemples de ports connus :

| Service | Port(s) |
| --- | --- |
| HTTP / HTTPS | 80 et 443 (… et 8080, voire 8443) |
| LDAP / LDAPS | 389 et 636 |
| SSH | 22 |
| DNS | 53 (… et 853, DoT) |
| FTP | 20 (données) et 21 (contrôle) |
| MS-KMS | 1688 (non officiel) |
| RADIUS | 1812 et 1813 |

<Warning titre="Le port n'indique pas toujours le protocole !">
    Utilisent HTTP (exemples) :

    - 631 : IPP (dont CUPS) ;
    - 3000 : Grafana ;
    - 8096 et 8920 : Jellyfin HTTP et HTTPS ;
    - 9090 et 9091 : administration OpenFire HTTP et HTTPS ;
    - … (vous n'êtes pas encore prêts !) …
    - 5000 : ASP.NET Core, Flask Framework Dev Webserver, Docker Registry, 3CX Management, AWS Elastic Beanstalk Proxy, Frigate NVR, Synology NAS…
</Warning>

<Remark titre="Historique">
    Les ports dits « bien connus » (*well-known*) ou ports « système » s'étendent de **0 à 1023**.

    - Il faut être administrateur (root) sous Unix-like pour les utiliser.
    - C'est moins vrai aujourd'hui, même si le principe persiste.
</Remark>

Autres plages :

{/* CORRIGÉ (reseaux.pdf p. 158 : la diapositive indiquait 51280 pour WireGuard). */}

- la plage des numéros « **enregistrés** » va de **1024 à 49151** ;
- la plage des numéros « **dynamiques** » (ou « éphémères ») va de **49152 à 65535** ;
- … bien que des applications en utilisent de manière statique mais non officielle (WireGuard 51820, ActiveMQ 61616…).

### Généricité des données

<Theorem type="Principe">
    La couche transport ne définit pas les données qu'elle transporte.
</Theorem>

**Proposition** : on peut choisir arbitrairement de changer les numéros de port par défaut. Mon serveur HTTP peut donc très bien aller en TCP/25 et mon serveur de courrier en TCP/80. Même si c'est peu recommandé !

### Poignée de main

<Definition titre="Poignée de main">
    Établir une connexion entre deux systèmes.
</Definition>

- Permet de s'assurer que la partie distante est bien présente.
- Implique un état de connexion (et son suivi).
- Permet de négocier des paramètres.

<Animation type="echange-sequence" titre="Poignée de main générique : exemple du 3-way handshake (reseaux.pdf p. 161)" params={{scenario: 'poignee-de-main'}}>
    Client → Service, Service → Client, Client → Service, puis échange de données (Data) dans les deux sens.
</Animation>

Des variantes existent, ainsi que des superpositions protocolaires.

### Les sockets

<Definition titre="Sockets">
    Les sockets sont les interfaces permettant à une application d'utiliser une pile réseau (API).
</Definition>

Par exemple sous Linux, il existe deux grandes familles :

- **socket AF_INET** : utilisation du réseau TCP/IP (adresse IP + port + protocole de transport) :
    - type « stream » : TCP ;
    - type « datagram » : UDP ;
- **socket AF_UNIX** : utilisation des canaux interprocessus (nom du fichier pivot + droits d'accès) ;
- **Winsock** : équivalent sous Windows ;
- **Raw** : mode brut au-dessus d'IP, donc sans mécanisme de transport.

Vous les verrez en cours de programmation, ce n'est pas l'objet de ce cours.

## Principe et fonctionnement d'UDP

<Definition titre="User Datagram Protocol (UDP)">
    Transmission de données **sans état**.
</Definition>

Ce que fournit UDP :

- somme de contrôle des datagrammes ;
- multiplexage à l'aide des 64k ports possibles ;
- et c'est tout !

### Le mode non connecté

<Theorem type="Principe">
    UDP est non connecté, donc les datagrammes sont émis **sans garantie de délivrance**.
</Theorem>

Cas d'utilisation d'UDP :

- flux audio et/ou vidéo avec débit adaptatif : la perte est compensée par l'encodage des données ;
- protocoles sans connexion à faible volumétrie : DNS (historiquement), Kerberos ;
- tunnels VPN : le tunnel n'a pas à suivre les connexions des couches supérieures.

## Principe et fonctionnement de TCP

<Definition titre="Transmission Control Protocol (TCP)">
    Transmission de données **avec état** et **garantie de délivrance**.
</Definition>

Ce que fournit TCP :

- somme de contrôle des segments ;
- multiplexage à l'aide des 64k ports possibles ;
- contrôle de congestion ;
- réordonnancement à l'arrivée ;
- déduplication ;
- garantie d'établissement de connexion.

### Le segment TCP

<Definition titre="Segment TCP">
    Le segment TCP est un élément de données et/ou de métadonnées d'une connexion TCP.

    **Principe lexical** : le segment a un début et une fin, et on peut enchaîner des segments : l'adresse de début du segment B suit immédiatement l'adresse de fin du segment A.
</Definition>

### Le mode connecté

<Theorem type="Principe">
    TCP est connecté : il fournit des garanties de délivrance, ou a minima de notification d'échec.
</Theorem>

Cas d'utilisation de TCP :

- transferts de fichiers : les données doivent arriver dans l'ordre ;
- système de commande à distance : les commandes, les acquittements et réponses doivent être émis et reçus avec fiabilité ;
- …

### La fenêtre TCP

<Definition titre="Fenêtre TCP">
    La fenêtre TCP permet d'envoyer une certaine quantité de données **sans attendre d'acquittement**.
</Definition>

- La fenêtre peut être agrandie ou réduite dynamiquement.
- La fenêtre « avance » au rythme des acquittements.
- Des mécanismes permettent d'optimiser l'utilisation de cette fenêtre.

### Échanger sur une connexion TCP

<Remark titre="Numéro d'acquittement">
    Le numéro d'acquittement est celui du **prochain octet attendu** : après avoir reçu les octets 257 à 512, le service répond ACK 513.
</Remark>

**Échange simple** : DATA seq 257-512 → ACK 513 ; DATA seq 513-768 → ACK 769.

</Animation>

**Acquittements multiples (fenêtre TCP = 1024)** : DATA seq 257-512, 513-768 et 769-1024 partent sans attendre ; un seul ACK 1025 revient.

    DATA seq 257-512, DATA seq 513-768, DATA seq 769-1024, puis ACK 1025.
</Animation>

**Perte d'un segment (sans optimisation)** : le segment 257-512 est perdu ; après le délai d'expiration (*timeout delay*), il est réémis puis acquitté (ACK 513).

<Animation type="echange-sequence" titre="Perte d'un segment, sans optimisation (reseaux.pdf p. 174)" params={{scenario: 'tcp-perte'}}>
    DATA seq 257-512 (perdu), Timeout delay, DATA seq 257-512, ACK 513.

{/* CORRIGÉ (reseaux.pdf p. 175 : la diapositive notait le dernier segment « 1536-1792 » (chevauchement avec 1281-1536)). */}

**Perte d'un segment : 3 acquittements dupliqués** : le segment 513-768 est perdu, les segments suivants (769-1024, 1025-1280, 1281-1536, 1537-1792) arrivent ; le service répond trois fois ACK 513 ; le client renvoie DATA seq 513-768 et reçoit ACK 1793.

</Animation>

### Indicateurs TCP (flags)

{/* CORRIGÉ (reseaux.pdf p. 179 : la diapositive listait « ECN » comme un indicateur ; c'est le mécanisme porté par ECE et CWR). */}

| Indicateur | Description |
| --- | --- |
| CWR | Indique la réduction de la fenêtre et le traitement d'une congestion |
| ECE | Indique la présence ou la capacité de gestion d'une congestion |
| URG | Signale des données urgentes |
| ACK | Acquittement de segments |
| PSH | Envoi de données (unilatéral) |
| RST | Fermeture anormale de la connexion |
| SYN | Demande d'établissement de connexion |
| FIN | Demande de fin de connexion |

<Remark>
    ECN (*Explicit Congestion Notification*) n'est pas un indicateur en soi : c'est le mécanisme de signalement de congestion, porté par les indicateurs ECE et CWR.
</Remark>

| État | Hôte concerné | Description |
| --- | --- | --- |
| LISTEN | SRV | En attente d'une requête distante |
| SYN-SENT | CLT | Demande de connexion envoyée |
| SYN-RECEIVED | SRV | Demande de connexion reçue |
| ESTABLISHED | CLI/SRV | Connexion établie |
| FIN-WAIT-1 | CLI/SRV | Fermeture active de connexion : émission « FIN » |
| FIN-WAIT-2 | CLI/SRV | Fin fermeture active : attente retour « FIN » |
| CLOSE-WAIT | CLI/SRV | Réception des dernières données et retour « FIN » |
| LAST-ACK | CLI/SRV | Attente de l'acquittement du dernier « FIN » |
| TIME-WAIT | CLI/SRV | Délai avant expiration des segments restants |
| CLOSED | CLI/SRV | Aucun état |

## Les contrôles de flux TCP

### Flux vs. congestion

<Definition titre="Contrôle de flux">
    S'applique entre l'émetteur et le récepteur, par exemple récepteur de faible capacité.
</Definition>

<Definition titre="Contrôle de congestion">
    Détecte un étranglement du réseau de transport.
</Definition>

### Maximum Segment Size (MSS)

<Definition titre="MSS">
    Fixe la taille maximale des données transportables dans un segment TCP.
</Definition>

{/* CORRIGÉ (reseaux.pdf p. 183 : la diapositive indiquait « MSS <= MTU - en-tête TCP », sans l'en-tête IP). */}

- Est liée à la MTU (`MSS <= MTU - en-tête IP - en-tête TCP`, soit 1500 − 20 − 20 = 1460 octets en IPv4 sur Ethernet).
- La MSS n'est pas calculée dynamiquement (comme peut l'être la MTU).

Généralement, MTU et MSS sont fixes, et à leurs valeurs par défaut, sauf cas de transport VPN ou liaisons exotiques.

### Ajustement de la bande passante

<Theorem type="Principe">
    Augmenter ou limiter le débit émis en élargissant ou réduisant la fenêtre TCP.
</Theorem>

**Problème** : si on augmente et qu'on diminue du même facteur (par addition ou par multiplication), on n'atteint jamais le point optimal !

### Additive Increase Multiplicative Decrease (AIMD)

{/* CORRIGÉ (reseaux.pdf p. 185-186 : les diapositives présentaient AIMD comme le mécanisme de démarrage et disaient que le slow start « suit le principe AIMD »). */}

- **Utilisation** : évitement de congestion (*congestion avoidance*), une fois la phase de slow start terminée.
- **Principe** : pour accélérer, ajouter la valeur de la MSS (valeur typique) ; pour ralentir, diviser de moitié le débit émis.
- **Objectif** : la bande passante utilisée finit par converger vers une valeur optimale.

### Slow start

<Theorem type="Principe">
    Se servir de la fenêtre de congestion pour accélérer progressivement.
</Theorem>

- L'accélération est **exponentielle** : la fenêtre de congestion augmente d'une MSS par acquittement reçu, donc double à chaque aller-retour.
- La perte d'un paquet déclenche le ralentissement en réduisant la fenêtre.
- Un paramètre « *slow start threshold* » permet de basculer en évitement de congestion (AIMD).

### Fast retransmit

<Theorem type="Principe">
    Renvoyer rapidement les paquets qui semblent perdus.
</Theorem>

Généralement, la réception de **3 ACK dupliqués** déclenche « fast retransmit ».

### Fast recovery

<Theorem type="Principe">
    Attendre l'ACK d'un segment perdu, voire de toute la fenêtre déjà envoyée après un « fast retransmit ».
</Theorem>

**Intérêt majeur** : éviter de repasser en mode « slow start ».

### Algorithmes de gestion de congestion TCP

- **TCP Tahoe** : Slow Start puis Congestion Avoidance (mais sans Fast Retransmit).
- **TCP Reno** : évolution de Tahoe pour utiliser Fast Retransmit.
- **TCP New Reno** : modification de Reno pour rester en mode Fast Recovery.
- **TCP Vegas** : n'attend plus la perte de paquet, mais se sert du Round Trip Time (RTT).
- **TCP Westwood** : réécriture de New Reno, modifie le comportement de divers mécanismes pour les rendre plus souples (gère RTT, « Agile Probing », Persistent Non Congestion Detection (PNCD)).
- **TCP SACK** : (Selective ACK) permet d'indiquer un segment perdu mais d'acquitter d'autres segments suivants.
- **TCP CUBIC** : élimine AIMD, plus du tout efficace sur nos réseaux n-Gigabit, recherche par dichotomie, Linux depuis 2.6.19.
- **TCP CTCP** : (Compound TCP), double fenêtre : RTT + BP, Windows depuis Vista.

### Et pour UDP ?

Tristement simple !

- Comme il n'existe aucun mécanisme de congestion…
- … UDP écrase TCP !
- UDP peut saturer la bande passante sans s'en apercevoir.

### Qualité de service sur les réseaux

<Definition titre="Qualité de service (QoS)">
    La QoS correspond à différents moyens et protocoles permettant de réguler et de prioriser le trafic sur les routeurs.
</Definition>

La gestion de la QoS sur les routeurs ne fait pas partie de ce cours.

## Autres protocoles du même niveau ou assimilés

### QUIC

<Definition titre="QUIC">
    QUIC propose une alternative à TCP pour le transport fiable en mode connecté.
</Definition>

Fonctionnalités majeures proposées :

- réémission de paquets perdus non bloquante ;
- chiffrement par TLS obligatoire ;
- déplacement du traitement en environnement utilisateur (et non noyau) ;
- simplification des poignées de main ;
- segmentation des données dans des flux ;
- itinérance de connexion ;
- est moins agressif qu'UDP sur la bande passante utilisée (QoS interne).

### RTP

<Definition titre="Real-time Transport Protocol (RTP)">
    Le Real-time Transport Protocol permet de transporter des données en « équivalent temps réel ».
</Definition>

Utilisation : flux voix (VoIP) ; visio et vidéoconférence ; parfois streaming vidéo (si pas en WebRTC).

Il peut être complété par *Real-Time Streaming Protocol* (RTSP) pour la télécommande et *Real-Time Control Protocol* (RTCP) s'il n'est pas utilisé par d'autres protocoles sachant le gérer comme SIP.

### SCTP

<Definition titre="Stream Control Transmission Protocol (SCTP)">
    SCTP propose de remplacer UDP et TCP en associant leurs atouts :

    - orienté message comme UDP ;
    - options pour le transport fiable comme TCP ;
    - options pour la fragmentation et le réassemblage comme TCP ;
    - options natives pour la redondance et la répartition de charge.
</Definition>

Utilisation : principalement par les opérateurs de téléphonie mobile pour la signalisation de la voix et les SMS.

### TLS

<Definition titre="Transport Layer Security (TLS)">
    TLS fournit un canal chiffré, généralement à l'aide d'authentification partielle ou complète avec de la cryptographie asymétrique.
</Definition>

Utilisation : TLS est utilisé notamment par HTTP : **HTTP sur TLS = HTTPS**.

**Poignée de main TLS** : SYN ; SYN + ACK ; ACK + ClientHello ; ServerHello + Cert ; ClientKeyExch + ChangeCipher ; ChangeCipher ; puis Data dans les deux sens.

<Animation type="echange-sequence" titre="Poignée de main TLS (reseaux.pdf p. 197)" params={{scenario: 'tls'}}>
    SYN, SYN + ACK, ACK + ClientHello, ServerHello + Cert, ClientKeyExch + ChangeCipher, ChangeCipher, Data, Data.
</Animation>

### DTLS

<Definition titre="DTLS">
    Fournir un équivalent de TLS sur UDP.
</Definition>

Utilisation : sécurisation de RTP (SRTP). C'est un protocole récent et encore peu utilisé.

## La translation d'adresse et de port

<Definition titre="Translation d'adresse (NAT)">
    Remplacer une adresse IP par une autre.
</Definition>

**Où faire ce type de manœuvre ?** Sur un routeur évidemment !

**Sens du changement** : changer l'adresse source : **SNAT** ; changer l'adresse destination : **DNAT**.

<Definition titre="Translation de port (PAT)">
    Remplacer un port UDP ou TCP par un autre.
</Definition>

**Où faire ce type de manœuvre ?** Sur un routeur évidemment ! … Même si parfois, c'est sur la même machine !

### Quand faire la translation ?

Ça dépend !

- Certaines modifications doivent se faire dès l'entrée dans le routeur…
- … d'autres doivent se faire juste avant la sortie définitive.

Vous verrez lorsque vous étudierez le pare-feu Netfilter (Linux) et la circulation des paquets dans le noyau.

### Translation d'adresse : cas d'utilisation n° 1

Franchissement sortant d'une box Internet. Déroulement et état du paquet IP :

| Étape | Description | SRCADDR | DSTADDR |
| --- | --- | --- | --- |
| 1 | Un hôte émet vers Internet via la passerelle | 192.168.1.110 | 192.0.2.115 |
| 2 | La passerelle échange son adresse | 203.0.113.198 | 192.0.2.115 |
| 3 | Le serveur distant répond | 192.0.2.115 | 203.0.113.198 |
| 4 | La passerelle renvoie en interne | 192.0.2.115 | 192.168.1.110 |

<Theorem type="Comment on appelle cette technique ?">
    Le **masquerading** ! La passerelle garde un état des connexions sortantes pour effectuer la traduction retour. La traduction se fait en sortie, c'est un cas particulier de SNAT.
</Theorem>

### Translation d'adresse : cas d'utilisation n° 2

Franchissement sortant d'un routeur avec personnalisation de l'adresse.

- Le principe est sensiblement identique.
- Il peut ne pas avoir à suivre l'état : association statique d'une adresse à une autre.
- Utilisé parfois sur des campus universitaires : hôte interne avec une adresse privée mais associée à une IP publique gérée par un routeur de bordure.
- C'est une sorte de « one-to-one NAT » (ou NAT 1:1).

### Translation de port : cas d'utilisation

Partage d'adresse IP chez Free.

- 4 abonnés Free se partagent une seule IP publique, la Freeteuse ne la voit plus directement par défaut.
- Seule une plage de ports TCP et UDP est relayée vers elle depuis Internet.
- En sortie les ports source peuvent être modifiés pour régler les conflits.

### La redirection d'adresse

<Definition titre="Redirection d'adresse">
    Rediriger une connexion entrante vers une autre adresse (généralement interne).
</Definition>

- Utilisé par exemple sur les box Internet pour exposer des services internes.
- On indique l'adresse interne à qui envoyer le trafic.
- Le réseau extérieur ne connaît que l'adresse de la passerelle.

Sous Linux : l'argument « jump-to » d'iptables, ou « dnat to » de nftables.

### La redirection de port

<Definition titre="Redirection de port">
    Rediriger une connexion entrante sur un port vers un autre port.
</Definition>

Cas d'utilisation : utilisé par exemple sur un serveur pour rediriger 80 vers 8080.

<Warning titre="Attention">
    On ne fait pas n'importe quoi ! Le protocole doit être identique, ou bien le client sait quel protocole parler : on ne fait pas du 80 vers 443 par PAT !
</Warning>

### Le cumul redirection adresse / port

<Definition titre="Cumul">
    Cumuler une translation d'adresse et une translation de port.
</Definition>

Cas d'utilisation :

- exposition d'un service interne par une Freeteuse : translation de l'adresse IP et du port. Par exemple : `192.0.2.110:443` vers `192.168.1.110:8443` ;
- exposition d'un service interne à un hôte : `192.168.1.110:443` vers `127.0.0.1:9091`.

### Quelques types de tunnels

<Definition titre="IP in IP">
    Transporte un paquet IP dans un autre paquet IP. Par exemple pour : IPv6 over IPv4 ; IPv4 over IPv6 ; pont IP entre deux LAN.
</Definition>

{/* CORRIGÉ (reseaux.pdf p. 211 : la diapositive indiquait le port UDP 47 pour GRE). */}

<Definition titre="Generic Routing Encapsulation (GRE)">
    Transport générique de données (pas forcément IP) :

    - soit directement au-dessus d'IP (proto 47) ;
    - soit via UDP (port 4754).
</Definition>

Tunnels dits « VPN » :

- **IPSec** : directement prévu par les protocoles IP : c'est bien IP qui est chiffré. Négociation des clés par logiciel externe. Complexe, mais très fiable notamment en entreprise.
- **OpenVPN** : tunnel de type SSL/TLS (niveau application). Logiciel et driver réseau à part entière. Vieillissant.
- **WireGuard** : tente de rassembler le meilleur des deux mondes : pilote noyau, sécurité par conception, manipulation relativement facile.

<Definition titre="Multiprotocol Label Switching (MPLS)">
    MPLS permet de transporter tout type de trafic : IPv4, IPv6, ATM, Ethernet… Apprécié des opérateurs pour les VPN intersite de leurs clients : très léger, très rapide, remplace le routage IP.
</Definition>

<Warning titre="Contrainte">
    Tous les routeurs de l'AS doivent gérer MPLS. Les bordures posent et enlèvent les étiquettes (inspiré du VLAN).
</Warning>
