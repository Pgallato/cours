## Principes élémentaires communs à TCP et UDP

### Le port

<Definition titre="Port">
    Le port sert à multiplexer et démultiplexer des communications sur un même hôte.
</Definition>

- Un port est codé sur 16 bits : il va donc de 0 à 65535.
- Certains numéros sont réservés et enregistrés auprès de l'IANA.
- Côté serveur, le numéro de port est souvent un indicateur fiable du service utilisé.
- Le port source et le port destination peuvent parfois être identiques.

Voici quelques ports connus :

| Service | Port(s) |
| --- | --- |
| HTTP / HTTPS | 80 et 443 (… et 8080, voire 8443) |
| LDAP / LDAPS | 389 et 636 |
| SSH | 22 |
| DNS | 53 (… et 853, DoT) |
| FTP | 20 (données) et 21 (contrôle) |
| MS-KMS | 1688 (non officiel) |
| RADIUS | 1812 et 1813 |

<Warning titre="Le port n'indique pas toujours le protocole !">
    Beaucoup de services utilisent HTTP sur un autre port que 80, par exemple :

    - 631 : IPP (dont CUPS) ;
    - 3000 : Grafana ;
    - 8096 et 8920 : Jellyfin en HTTP et en HTTPS ;
    - 9090 et 9091 : administration d'OpenFire en HTTP et en HTTPS ;
    - 5000 : ASP.NET Core, le serveur de développement de Flask, Docker Registry, l'administration de 3CX, le proxy d'AWS Elastic Beanstalk, Frigate NVR, les NAS Synology…
</Warning>

<Remark titre="Historique">
    Les ports dits « bien connus » (*well-known*) ou ports « système » s'étendent de **0 à 1023**.

    Sur les systèmes de type Unix, il fallait être administrateur (root) pour les utiliser. C'est moins vrai aujourd'hui, même si le principe persiste.
</Remark>

Les autres numéros se répartissent en deux plages :

{/* CORRIGÉ (reseaux.pdf p. 158 : la diapositive indiquait 51280 pour WireGuard). */}

- la plage des numéros « **enregistrés** » va de **1024 à 49151** ;
- la plage des numéros « **dynamiques** » (ou « éphémères ») va de **49152 à 65535**, même si certaines applications y utilisent un port fixe de manière non officielle (WireGuard 51820, ActiveMQ 61616…).

### Généricité des données

<Theorem type="Principe">
    La couche transport ne définit pas les données qu'elle transporte.
</Theorem>

On peut donc choisir librement de changer les numéros de port par défaut : un serveur HTTP peut très bien écouter sur le port TCP 25 et un serveur de courrier sur le port TCP 80, même si c'est peu recommandé.

### Poignée de main

<Definition titre="Poignée de main">
    Échange initial qui établit une connexion entre deux systèmes.
</Definition>

La poignée de main permet de s'assurer que la partie distante est bien présente et de négocier des paramètres. Elle implique un état de connexion, qu'il faut ensuite suivre.

<Animation type="echange-sequence" titre="Poignée de main générique : exemple du 3-way handshake (reseaux.pdf p. 161)" params={{scenario: 'poignee-de-main'}}>
    Client → Service, Service → Client, Client → Service, puis échange de données (Data) dans les deux sens.
</Animation>

Des variantes existent, ainsi que des superpositions protocolaires.

### Les sockets

<Definition titre="Sockets">
    Les sockets sont les interfaces permettant à une application d'utiliser une pile réseau (API).
</Definition>

Sous Linux, par exemple, il existe deux grandes familles de sockets :

- les **sockets AF_INET** utilisent le réseau TCP/IP (adresse IP, port et protocole de transport) ; elles sont de type « stream » pour TCP et de type « datagram » pour UDP ;
- les **sockets AF_UNIX** utilisent les canaux de communication entre processus (nom du fichier pivot et droits d'accès).

Sous Windows, l'équivalent s'appelle **Winsock**. Il existe enfin des sockets **Raw**, en mode brut au-dessus d'IP, donc sans mécanisme de transport.

Les sockets sont étudiées en cours de programmation ; elles ne sont pas l'objet de ce cours.

## Principe et fonctionnement d'UDP

<Definition titre="User Datagram Protocol (UDP)">
    Protocole de transmission de données **sans état**.
</Definition>

UDP fournit seulement une somme de contrôle des datagrammes et le multiplexage grâce aux 65 536 ports possibles.

### Le mode non connecté

<Theorem type="Principe">
    UDP est non connecté, donc les datagrammes sont émis **sans garantie de délivrance**.
</Theorem>

UDP est utilisé par exemple pour :

- les flux audio ou vidéo à débit adaptatif, où l'encodage des données compense les pertes ;
- les protocoles sans connexion et peu volumineux, comme DNS (historiquement) ou Kerberos ;
- les tunnels VPN, qui n'ont pas à suivre les connexions des couches supérieures.

## Principe et fonctionnement de TCP

<Definition titre="Transmission Control Protocol (TCP)">
    Protocole de transmission de données **avec état** et **garantie de délivrance**.
</Definition>

TCP fournit :

- une somme de contrôle des segments ;
- le multiplexage grâce aux 65 536 ports possibles ;
- un contrôle de congestion ;
- la remise dans l'ordre des segments à l'arrivée ;
- la suppression des doublons ;
- la garantie d'établissement de la connexion.

### Le segment TCP

<Definition titre="Segment TCP">
    Le segment TCP est un élément de données et/ou de métadonnées d'une connexion TCP.

    Un segment a un début et une fin, et les segments s'enchaînent : le début du segment B suit immédiatement la fin du segment A.
</Definition>

### Le mode connecté

<Theorem type="Principe">
    TCP est connecté : il fournit des garanties de délivrance, ou a minima de notification d'échec.
</Theorem>

TCP est utilisé par exemple pour :

- les transferts de fichiers, où les données doivent arriver dans l'ordre ;
- les systèmes de commande à distance, où les commandes, les acquittements et les réponses doivent être émis et reçus de façon fiable.

### La fenêtre TCP

<Definition titre="Fenêtre TCP">
    La fenêtre TCP permet d'envoyer une certaine quantité de données **sans attendre d'acquittement**.
</Definition>

La fenêtre peut être agrandie ou réduite dynamiquement, et elle « avance » au rythme des acquittements. Divers mécanismes permettent d'optimiser son utilisation.

### Échanger sur une connexion TCP

### Indicateurs TCP (flags)

{/* CORRIGÉ (reseaux.pdf p. 179 : la diapositive listait « ECN » comme un indicateur ; c'est le mécanisme porté par ECE et CWR). */}

| Indicateur | Description |
| --- | --- |
| CWR | Indique la réduction de la fenêtre et le traitement d'une congestion |
| ECE | Indique la présence ou la capacité de gestion d'une congestion |
| URG | Signale des données urgentes |
| ACK | Acquittement de segments |
| PSH | Envoi de données (unilatéral) |
| RST | Fermeture anormale de la connexion |
| SYN | Demande d'établissement de connexion |
| FIN | Demande de fin de connexion |

<Remark>
    ECN (*Explicit Congestion Notification*) n'est pas un indicateur en soi : c'est le mécanisme de signalement de congestion, porté par les indicateurs ECE et CWR.
</Remark>

### Résumé des états TCP

| État | Hôte concerné | Description |
| --- | --- | --- |
| LISTEN | SRV | En attente d'une requête distante |
| SYN-SENT | CLT | Demande de connexion envoyée |
| SYN-RECEIVED | SRV | Demande de connexion reçue |
| ESTABLISHED | CLI/SRV | Connexion établie |
| FIN-WAIT-1 | CLI/SRV | Fermeture active de connexion : émission « FIN » |
| FIN-WAIT-2 | CLI/SRV | Fin fermeture active : attente retour « FIN » |
| CLOSE-WAIT | CLI/SRV | Réception des dernières données et retour « FIN » |
| LAST-ACK | CLI/SRV | Attente de l'acquittement du dernier « FIN » |
| TIME-WAIT | CLI/SRV | Délai avant expiration des segments restants |
| CLOSED | CLI/SRV | Aucun état |

## Les contrôles de flux TCP

### Flux vs. congestion

<Definition titre="Contrôle de flux">
    Il régule les échanges entre l'émetteur et le récepteur, par exemple lorsque le récepteur a une faible capacité.
</Definition>

<Definition titre="Contrôle de congestion">
    Il détecte un engorgement du réseau de transport.
</Definition>

### Maximum Segment Size (MSS)

<Definition titre="MSS">
    La MSS fixe la taille maximale des données qu'un segment TCP peut transporter.
</Definition>

{/* CORRIGÉ (reseaux.pdf p. 183 : la diapositive indiquait « MSS <= MTU - en-tête TCP », sans l'en-tête IP). */}

Elle est liée à la MTU : `MSS <= MTU - en-tête IP - en-tête TCP`, soit 1500 − 20 − 20 = 1460 octets en IPv4 sur Ethernet. Contrairement à la MTU, elle n'est pas calculée dynamiquement.

En général, MTU et MSS restent fixes, à leurs valeurs par défaut, sauf dans le cas d'un transport par VPN ou de liaisons particulières.

### Ajustement de la bande passante

<Theorem type="Principe">
    On augmente ou on limite le débit émis en élargissant ou en réduisant la fenêtre TCP.
</Theorem>

Cependant, si l'on augmente et diminue le débit du même facteur (par addition ou par multiplication dans les deux sens), on n'atteint jamais le point optimal.

### Additive Increase Multiplicative Decrease (AIMD)

{/* CORRIGÉ (reseaux.pdf p. 185-186 : les diapositives présentaient AIMD comme le mécanisme de démarrage et disaient que le slow start « suit le principe AIMD »). */}

AIMD est utilisé pour l'évitement de congestion (*congestion avoidance*), une fois la phase de slow start terminée. Pour accélérer, on ajoute une MSS (valeur typique) à la fenêtre ; pour ralentir, on divise le débit émis par deux. La bande passante utilisée finit ainsi par converger vers une valeur optimale.

### Slow start

<Theorem type="Principe">
    On se sert de la fenêtre de congestion pour accélérer progressivement.
</Theorem>

L'accélération est **exponentielle** : la fenêtre de congestion augmente d'une MSS à chaque acquittement reçu, et double donc à chaque aller-retour. La perte d'un paquet déclenche un ralentissement en réduisant la fenêtre. Un seuil, le « *slow start threshold* », permet de basculer en évitement de congestion (AIMD).

### Fast retransmit

<Theorem type="Principe">
    On renvoie rapidement les paquets qui semblent perdus.
</Theorem>

En général, c'est la réception de **3 ACK dupliqués** qui déclenche le « fast retransmit ».

### Fast recovery

<Theorem type="Principe">
    Après un « fast retransmit », on attend l'acquittement du segment perdu, voire de toute la fenêtre déjà envoyée.
</Theorem>

Son intérêt majeur est d'éviter de repasser en mode « slow start ».

### Algorithmes de gestion de congestion TCP

- **TCP Tahoe** enchaîne Slow Start puis Congestion Avoidance, mais sans Fast Retransmit.
- **TCP Reno** fait évoluer Tahoe pour utiliser Fast Retransmit.
- **TCP New Reno** modifie Reno pour rester en mode Fast Recovery.
- **TCP Vegas** n'attend plus la perte d'un paquet : il se sert du temps d'aller-retour (*Round Trip Time*, RTT).
- **TCP Westwood** réécrit New Reno et assouplit divers mécanismes : prise en compte du RTT, « Agile Probing », *Persistent Non Congestion Detection* (PNCD).
- **TCP SACK** (*Selective ACK*) permet de signaler un segment perdu tout en acquittant les segments suivants.
- **TCP CUBIC** abandonne AIMD, devenu inefficace sur les réseaux à plusieurs gigabits, au profit d'une recherche par dichotomie ; il est utilisé par Linux depuis la version 2.6.19.
- **TCP CTCP** (*Compound TCP*) utilise une double fenêtre, fondée sur le RTT et sur la bande passante ; il est utilisé par Windows depuis Vista.

### Et pour UDP ?

UDP ne dispose d'aucun mécanisme de contrôle de congestion. Il peut donc saturer la bande passante sans s'en apercevoir, et prendre le dessus sur TCP, qui réduit son débit.

### Qualité de service sur les réseaux

<Definition titre="Qualité de service (QoS)">
    La QoS regroupe différents moyens et protocoles qui permettent de réguler le trafic sur les routeurs et de lui donner des priorités.
</Definition>

La gestion de la QoS sur les routeurs ne fait pas partie de ce cours.

## Autres protocoles du même niveau ou assimilés

### QUIC

<Definition titre="QUIC">
    QUIC propose une alternative à TCP pour le transport fiable en mode connecté.
</Definition>

Ses principales fonctionnalités sont :

- la réémission non bloquante des paquets perdus ;
- le chiffrement obligatoire par TLS ;
- un traitement déplacé dans l'espace utilisateur (et non plus dans le noyau) ;
- des poignées de main simplifiées ;
- le découpage des données en flux ;
- l'itinérance des connexions ;
- une consommation de bande passante moins agressive qu'UDP (QoS interne).

### RTP

<Definition titre="Real-time Transport Protocol (RTP)">
    Le Real-time Transport Protocol permet de transporter des données en « équivalent temps réel ».
</Definition>

Il sert aux flux de voix (VoIP), à la visioconférence et parfois au streaming vidéo (lorsque WebRTC n'est pas utilisé).

Il peut être complété par le *Real-Time Streaming Protocol* (RTSP), qui sert de télécommande, et par le *Real-Time Control Protocol* (RTCP), sauf si d'autres protocoles comme SIP assurent déjà ce contrôle.

### SCTP

<Definition titre="Stream Control Transmission Protocol (SCTP)">
    SCTP propose de remplacer UDP et TCP en associant leurs atouts :

    - il est orienté message, comme UDP ;
    - il propose des options de transport fiable, comme TCP ;
    - il propose des options de fragmentation et de réassemblage, comme TCP ;
    - il gère nativement la redondance et la répartition de charge.
</Definition>

Il est surtout utilisé par les opérateurs de téléphonie mobile pour la signalisation de la voix et pour les SMS.

### TLS

<Definition titre="Transport Layer Security (TLS)">
    TLS fournit un canal chiffré, généralement avec une authentification partielle ou complète fondée sur la cryptographie asymétrique.
</Definition>

TLS est notamment utilisé par HTTP : **HTTP sur TLS = HTTPS**.

La **poignée de main TLS** se déroule ainsi : SYN ; SYN + ACK ; ACK + ClientHello ; ServerHello + Cert ; ClientKeyExch + ChangeCipher ; ChangeCipher ; puis échange de données (Data) dans les deux sens.

<Animation type="echange-sequence" titre="Poignée de main TLS (reseaux.pdf p. 197)" params={{scenario: 'tls'}}>
    SYN, SYN + ACK, ACK + ClientHello, ServerHello + Cert, ClientKeyExch + ChangeCipher, ChangeCipher, Data, Data.
</Animation>

### DTLS

<Definition titre="DTLS">
    DTLS fournit un équivalent de TLS sur UDP.
</Definition>

Il sert notamment à sécuriser RTP (SRTP). C'est un protocole récent et encore peu utilisé.

## La translation d'adresse et de port

<Definition titre="Translation d'adresse (NAT)">
    La translation d'adresse consiste à remplacer une adresse IP par une autre.
</Definition>

Cette opération se fait sur un routeur. Si l'on change l'adresse source, on parle de **SNAT** ; si l'on change l'adresse de destination, on parle de **DNAT**.

<Definition titre="Translation de port (PAT)">
    La translation de port consiste à remplacer un port UDP ou TCP par un autre.
</Definition>

Elle se fait elle aussi sur un routeur, mais parfois directement sur la machine concernée.

### Quand faire la translation ?

Cela dépend des cas : certaines modifications doivent être faites dès l'entrée du paquet dans le routeur, d'autres juste avant sa sortie définitive. Vous le verrez en étudiant le pare-feu Netfilter (Linux) et la circulation des paquets dans le noyau.

### Translation d'adresse : cas d'utilisation n° 1

Prenons un paquet qui sort d'un réseau domestique en traversant une box Internet. Voici son déroulement et l'état du paquet IP à chaque étape :

| Étape | Description | SRCADDR | DSTADDR |
| --- | --- | --- | --- |
| 1 | Un hôte émet vers Internet via la passerelle | 192.168.1.110 | 192.0.2.115 |
| 2 | La passerelle échange son adresse | 203.0.113.198 | 192.0.2.115 |
| 3 | Le serveur distant répond | 192.0.2.115 | 203.0.113.198 |
| 4 | La passerelle renvoie en interne | 192.0.2.115 | 192.168.1.110 |

<Theorem type="Masquerading">
    Cette technique s'appelle le **masquerading**. La passerelle garde un état des connexions sortantes pour effectuer la traduction retour. La traduction se fait en sortie : c'est un cas particulier de SNAT.
</Theorem>

### Translation d'adresse : cas d'utilisation n° 2

Un paquet peut aussi sortir par un routeur qui lui attribue une adresse personnalisée. Le principe est sensiblement le même, mais le routeur n'a pas forcément besoin de suivre l'état des connexions : une adresse est associée statiquement à une autre. Cette technique est parfois utilisée sur les campus universitaires, où un hôte interne a une adresse privée associée à une adresse publique gérée par le routeur de bordure. C'est une sorte de « one-to-one NAT » (ou NAT 1:1).

### Translation de port : cas d'utilisation

Free utilise la translation de port pour partager des adresses IP. Quatre abonnés se partagent une seule adresse IP publique, si bien que, par défaut, la Freebox ne la voit plus directement. Seule une plage de ports TCP et UDP lui est relayée depuis Internet, et en sortie, les ports source peuvent être modifiés pour éviter les conflits.

### La redirection d'adresse

<Definition titre="Redirection d'adresse">
    La redirection d'adresse envoie une connexion entrante vers une autre adresse, généralement interne.
</Definition>

Elle est utilisée par exemple sur les box Internet pour exposer des services internes : on indique l'adresse interne à laquelle envoyer le trafic, et le réseau extérieur ne connaît que l'adresse de la passerelle.

Sous Linux, on utilise l'argument « jump-to » d'iptables ou « dnat to » de nftables.

### La redirection de port

<Definition titre="Redirection de port">
    La redirection de port envoie une connexion entrante sur un port vers un autre port.
</Definition>

On l'utilise par exemple sur un serveur pour rediriger le port 80 vers le port 8080.

<Warning titre="Attention">
    Le protocole doit rester le même, ou bien le client doit savoir quel protocole parler : on ne redirige pas le port 80 vers le port 443 par PAT.
</Warning>

### Le cumul redirection adresse / port

<Definition titre="Cumul">
    On peut combiner une translation d'adresse et une translation de port.
</Definition>

C'est le cas par exemple :

- pour exposer un service interne derrière une Freebox, en traduisant l'adresse IP et le port, par exemple de `192.0.2.110:443` vers `192.168.1.110:8443` ;
- pour exposer un service local à un hôte, par exemple de `192.168.1.110:443` vers `127.0.0.1:9091`.

### Quelques types de tunnels

<Definition titre="IP in IP">
    Un paquet IP est transporté dans un autre paquet IP, par exemple pour faire passer IPv6 sur IPv4, IPv4 sur IPv6, ou pour créer un pont IP entre deux LAN.
</Definition>

{/* CORRIGÉ (reseaux.pdf p. 211 : la diapositive indiquait le port UDP 47 pour GRE). */}

<Definition titre="Generic Routing Encapsulation (GRE)">
    GRE transporte des données de façon générique (pas forcément IP) :

    - soit directement au-dessus d'IP (protocole 47) ;
    - soit via UDP (port 4754).
</Definition>

Parmi les tunnels dits « VPN », on trouve :

- **IPSec**, directement prévu par les protocoles IP : c'est bien IP qui est chiffré. Les clés sont négociées par un logiciel externe. Il est complexe, mais très fiable, notamment en entreprise.
- **OpenVPN**, un tunnel de type SSL/TLS (niveau application), qui comprend un logiciel et un pilote réseau à part entière. Il est vieillissant.
- **WireGuard**, qui tente de réunir le meilleur des deux mondes : pilote noyau, sécurité dès la conception et prise en main relativement facile.

<Definition titre="Multiprotocol Label Switching (MPLS)">
    MPLS permet de transporter tout type de trafic : IPv4, IPv6, ATM, Ethernet… Très léger et très rapide, il remplace le routage IP ; les opérateurs l'apprécient pour les VPN entre les sites de leurs clients.
</Definition>

<Warning titre="Contrainte">
    Tous les routeurs du système autonome (AS) doivent gérer MPLS. Les routeurs de bordure posent et retirent les étiquettes, sur un principe inspiré du VLAN.
</Warning>
